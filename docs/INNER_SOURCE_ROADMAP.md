# Inner Source 도입 로드맵

## 1. 문서 개요

- **프로젝트:** week-6 OSS Collaboration Project
- **도입 대상:** 가상의 중소규모 IT 기업
- **도입 기간:** 12주
- **진행 방식:** 단계별 시범 운영 후 확대
- **문서 상태:** Proposed (도입 계획 초안)

본 문서는 조직 내부에 오픈소스 개발 방식인 Inner Source를 도입하기 위한 계획을 수립하는 것을 목적으로 합니다.

실제 조직에 적용한 결과가 아닌, 조직 내부 협업 체계를 설계하기 위한 가상 시나리오입니다.

## 2. Inner Source 도입 배경

일반적인 조직에서는 개발팀마다 독립적으로 프로젝트를 운영하는 경우가 많습니다.

이러한 구조에서는 다음 문제가 발생할 수 있습니다.

- 서로 다른 팀이 비슷한 기능을 중복 개발합니다.
- 기존 코드를 다른 팀이 활용하기 어렵습니다.
- 팀 간 지식과 기술 경험이 충분히 공유되지 않습니다.
- 특정 개발자에게 유지보수 업무가 집중됩니다.
- 협업 과정과 기술적 의사결정 기록이 부족합니다.

Inner Source는 조직 내부에서 코드, 문서, 개발 과정을 공유하고 다른 팀의 참여를 허용하여 이러한 문제를 개선하는 접근 방식입니다.

## 3. 도입 목표

이번 프로젝트에서는 다음 다섯 가지 목표를 설정합니다.

1. 조직 내부의 코드 재사용성을 향상합니다.
2. 팀 사이의 기술적 협업을 활성화합니다.
3. 코드 리뷰와 문서화 과정을 표준화합니다.
4. 중복 개발과 유지보수 비용을 줄입니다.
5. 특정 개발자에게 집중된 지식을 조직 전체로 확산합니다.

## 4. Inner Source 운영 원칙

### 4.1 개방성 (Openness)

조직 내부에서 공유 가능한 프로젝트를 구성원이 쉽게 찾고 접근할 수 있도록 합니다.

단, 외부에 공개할 수 없는 코드와 민감한 정보는 별도의 접근 통제를 적용합니다.

### 4.2 투명성 (Transparency)

개발 이력, 기술적 의사결정, Issue, Pull Request 등을 기록하여 변경 이유를 이해할 수 있도록 합니다.

### 4.3 멘토링 우선 (Prioritized Mentorship)

프로젝트 담당자는 신규 기여자가 쉽게 참여할 수 있도록 기여 절차를 안내하고 코드 리뷰를 지원합니다.

### 4.4 자발적 기여 (Voluntary Contribution)

다른 팀의 개발자는 자신의 업무와 관련된 프로젝트에 자발적으로 참여하고 개선 사항을 제안할 수 있습니다.

## 5. 단계별 도입 로드맵

### 1단계. 도입 준비 (1~2주 차)

**목표:** 조직 내부 협업 환경과 기본 규칙 수립

주요 작업:
- 현재 팀별 개발 방식과 중복 기능 조사
- Inner Source 적용 후보 프로젝트 선정
- GitHub Organization 및 저장소 권한 정책 검토
- README, CONTRIBUTING, CODE_OF_CONDUCT 문서 표준화
- 프로젝트별 코드 담당자 지정
- 내부 공유가 가능한 코드와 제한이 필요한 코드 분류

담당 역할:
- 프로젝트 관리자: 도입 계획 수립
- 기술 리더: 후보 프로젝트 선정
- 보안 담당자: 접근 권한 및 정보 보호 기준 검토

**완료 기준**
- 시범 프로젝트 1개 선정
- 협업 가이드 초안 완성
- 저장소 접근 권한 정책 수립

### 2단계. 시범 운영 (3~5주 차)

**목표:** 제한된 프로젝트에서 Inner Source 협업 방식 검증

주요 작업:
- 공통 유틸리티 또는 재사용 가능한 기능을 시범 프로젝트로 선정
- 내부 기여자가 참여할 수 있는 저장소 운영
- Issue를 활용한 개선 요청 접수
- Feature 브랜치 및 Pull Request 기반 개발
- CODEOWNERS를 활용한 리뷰 담당자 지정
- 신규 기여자를 위한 가이드 및 멘토링 제공
- 코드 리뷰 및 병합 과정 기록

담당 역할:
- 시범 프로젝트 담당팀: 프로젝트 운영
- 기여 개발자: 기능 개선 및 버그 수정
- 리뷰 담당자: 변경 사항 검토 및 피드백

**완료 기준**
- 다른 팀의 기여 PR 2건 이상 시도
- 리뷰 절차 검증
- 프로젝트 사용 및 기여 문서 검토 완료

### 3단계. 적용 확대 (6~9주 차)

**목표:** 여러 팀으로 Inner Source 운영 방식 확대

주요 작업:
- 시범 운영 결과 분석
- 공통 코드 및 재사용 가능한 프로젝트 목록 구축
- 팀별 저장소 운영 규칙 표준화
- 기여자 및 리뷰어 역할 명확화
- GitHub Actions를 통한 테스트 자동화 검토
- 기술 변경 사항을 RFC 및 ADR로 기록
- 신규 참여자를 위한 교육 자료 제작

담당 역할:
- 프로젝트 관리자: 적용 범위 확대
- 기술 리더: 코드 품질 및 재사용 기준 관리
- 팀별 담당자: 신규 참여자 지원

**완료 기준**
- 참여팀 3개 이상 확보
- 내부 공유 프로젝트 2개 이상 등록
- 공통 협업 가이드 배포

### 4단계. 성과 평가 및 개선 (10~12주 차)

**목표:** 도입 효과를 측정하고 지속적인 운영 체계 확립

주요 작업:
- 팀 간 코드 기여 현황 분석
- Pull Request 리뷰 및 병합 소요 시간 확인
- 공통 코드 재사용 사례 조사
- 개발자 만족도 및 운영 개선 의견 수집
- 병목 구간과 미해결 문제 분석
- 다음 분기 운영 계획 수립
- Inner Source 운영 책임과 유지보수 체계 확정

담당 역할:
- 프로젝트 관리자: 성과 평가 총괄
- 기술 리더: 기술적 개선 과제 도출
- 참여 개발자: 만족도 및 피드백 제공

**완료 기준**
- 성과 측정 보고서 작성
- 문제점 및 개선 사항 도출
- 다음 운영 계획 수립

## 6. 전체 일정 요약

| 단계 | 기간 | 핵심 활동 | 주요 산출물 |
|---|---|---|---|
| 준비 | 1~2주 | 규칙 및 권한 설계 | 운영 정책 |
| 시범 운영 | 3~5주 | PR 협업 실습 | 시범 프로젝트 |
| 적용 확대 | 6~9주 | 팀 간 공유 확대 | 공통 프로젝트 목록 |
| 성과 평가 | 10~12주 | KPI 분석 및 개선 | 성과 보고서 |

## 7. GitHub 기반 협업 운영 방안

### 저장소 관리

- 조직 내부 공유 프로젝트는 승인된 비공개 저장소를 기본으로 운영합니다.
- 내부 구성원이 프로젝트를 찾을 수 있도록 저장소 설명과 문서를 관리합니다.
- 민감 정보나 인증 키는 저장소에 포함하지 않습니다.
- 접근 권한은 업무상 필요한 범위로 제한합니다.

### 브랜치 전략

- `main`: 안정적인 코드 관리
- `feature/*`: 신규 기능 개발
- `fix/*`: 버그 수정
- `docs/*`: 문서 수정

### Pull Request 운영

1. Issue를 등록하여 문제를 정의합니다.
2. 작업 브랜치를 생성합니다.
3. 기능을 구현하고 커밋합니다.
4. PR을 생성하여 변경 사항을 설명합니다.
5. 담당자의 코드 리뷰를 받습니다.
6. 수정 사항을 반영하고 테스트합니다.
7. 병합 조건을 충족하면 main에 반영합니다.

### 리뷰 규칙

- `[MUST]`: 반드시 수정해야 하는 문제
- `[SHOULD]`: 품질 향상을 위해 개선을 권장하는 문제

최종 병합 권한은 프로젝트 담당자 또는 지정된 리뷰어에게 부여합니다.

## 8. 조직 내부 역할과 책임

| 역할 | 주요 책임 |
|---|---|
| 프로젝트 관리자 | 운영 정책, 일정 및 성과 관리 |
| 프로젝트 담당팀(Host Team) | 코드 유지보수 및 기여 검토 |
| 기여 개발자(Contributor) | 개선 제안, 코드 수정 및 테스트 |
| 신뢰 기여자(Trusted Committer) | 지속적인 리뷰, 멘토링 및 품질 관리 |
| 보안 담당자 | 접근 권한 및 정보 보호 정책 검토 |

프로젝트 규모에 따라 한 사람이 여러 역할을 맡을 수 있습니다.

## 9. 성과 측정 지표(KPI)

도입 성과를 평가하기 위해 다음 지표를 활용합니다.

| 지표 | 12주 차 목표 |
|---|---|
| 참여 개발팀 수 | 3개 이상 |
| 내부 공유 프로젝트 | 2개 이상 |
| 다른 팀에서 제출한 PR | 누적 5건 이상 |
| PR 최초 리뷰 시간 | 중앙값 2영업일 이내 |
| 공통 코드 재사용 사례 | 3건 이상 |
| 참여 개발자 만족도 | 5점 만점 중 4점 이상 |

위 수치는 실제 성과가 아니라 시범 도입의 목표값입니다.

도입 전 기준값을 조사하고, 12주 차 결과와 비교하여 효과를 평가합니다.

단순 PR 개수뿐 아니라 기여 품질, 팀 간 협업 경험, 실제 코드 재사용 여부를 함께 확인합니다.

## 10. 예상 위험 및 대응 방안

### 10.1 다른 팀의 코드 수정에 대한 거부감

**위험:** 기존 담당팀이 외부 기여를 부담스럽게 생각할 수 있습니다.

**대응:** 코드 리뷰 권한과 병합 책임을 명확히 하고, 소규모 수정부터 참여하도록 지원합니다.

### 10.2 보안 및 정보 유출

**위험:** 내부 전용 코드나 민감한 정보가 의도하지 않은 사용자에게 공유될 수 있습니다.

**대응:** 저장소 접근 통제, 비밀정보 검사, 보안 검토 절차를 적용합니다.

### 10.3 리뷰 업무 증가

**위험:** 기여가 늘면서 담당자의 리뷰 부담이 증가할 수 있습니다.

**대응:** 리뷰 담당자를 분산하고, 자동화된 테스트 및 리뷰 체크리스트를 활용합니다.

### 10.4 참여율 부족

**위험:** 개발자가 기존 업무 때문에 다른 팀 프로젝트에 참여하기 어려울 수 있습니다.

**대응:** 기여 활동을 업무 성과로 인정하고, 작은 개선 과제를 마련합니다.

## 11. OSS와 Inner Source의 차이

| 구분 | Open Source | Inner Source |
|---|---|---|
| 협업 대상 | 외부 개발자 포함 | 조직 내부 구성원 중심 |
| 코드 공개 범위 | 공개 라이선스에 따라 외부 배포 | 조직의 접근 정책에 따름 |
| 협업 방식 | Issue, PR, 리뷰 | Issue, PR, 리뷰 |
| 주요 목적 | 공개 협업 및 소프트웨어 공유 | 내부 코드 재사용 및 협업 개선 |

Inner Source는 내부 협업 방식이므로 모든 코드를 외부에 공개할 필요가 없습니다.

또한 조직 내부 코드에 적용되는 지식재산권 및 이용 정책은 별도로 관리해야 합니다.

## 12. 기대 효과

Inner Source 도입을 통해 다음과 같은 효과를 기대합니다.

- 개발팀 사이의 중복 작업 감소
- 공통 기능의 재사용 증가
- 코드 품질 및 문서화 수준 향상
- 팀 간 기술 지식 공유 확대
- 신규 개발자의 프로젝트 적응 지원
- 조직 전체의 유지보수 효율 향상

## 13. 결론

Inner Source는 단순히 조직 내부에 소스 코드를 공개하는 것이 아니라, 서로 다른 팀이 공동으로 소프트웨어를 개선할 수 있는 협업 체계를 구축하는 접근 방식입니다.

따라서 초기에는 제한된 프로젝트에서 시범 운영하고, 기여 절차와 보안 정책을 검증한 뒤 점진적으로 확대하는 것이 적절합니다.

본 로드맵에서는 12주 동안 준비, 시범 운영, 적용 확대, 성과 평가의 네 단계를 수행하도록 계획하였습니다.

향후 실제 조직에 적용할 경우에는 구성원의 참여 수준과 프로젝트 규모에 따라 일정 및 목표 지표를 조정해야 합니다.
